# The Gutter Pass runs last, over context the other Passes leave on each Line

The Log View gets a Gutter, two cells wide down its left side, where marks about each Line are shown beside it, starting with `>` beside the Current Line. What a mark shows depends on what the Passes have worked out about the Line, and a mark must move with its Line on Scroll and as new Lines arrive. So each Line carries two new fields (in `reader`): `GutterContext`, the context the Passes leave for the Gutter, grouped by the Pass that sets it (for now `GutterContext.Search.Current`, set by the Search on the Current Line), and `Gutter`, a fixed array of `GutterWidth` (2) runes, 0 meaning an empty cell. A Gutter Pass, run by the Executor after the Search, turns each Line's `GutterContext` into its `Gutter` cells, so it sees each Line as every other Pass leaves it. The Search's port still reads Lines as the Passes before the Search leave them; the Gutter Pass never runs there. The Executor's `GetWindow` returns the shown text and the Gutter cells from the same read, each joined by newlines, so their rows always line up; the Log View draws the Gutter inside its border, on its own background, as tall as the Log View. The Search still remembers the Current Line's Line Number itself, as its stepping state, since a Line is copied fresh on every read. We rejected having the UI ask the Search for the Current Line and draw the mark itself (the UI would have to match Line Numbers to rows, and every later mark would need its own call), and letting each Pass write Gutter cells directly (two Passes could fight over a cell, and no one place would decide what the Gutter shows).

Amended: context left on a Line is not only for the Gutter. Any Pass may read context a Pass run before it leaves on a Line. The Filter, run first, before every other Pass, sets `Filter.Hide` on each Line its regex doesn't match, and the Search reads it to pass over hidden Lines when stepping, since its port reads Lines as those Passes leave them. `GetWindow` leaves hidden Lines out of both the shown text and the Gutter cells, so their rows still line up, while `Lines()` keeps every Line with its context. We rejected giving the Search a port that returns only the Lines the Filter does not hide: the Search's stepping would then depend on which Passes the port runs, rather than on the Lines it reads.

## Consequences

- The Search no longer runs last: the Gutter Pass runs after it. The Executor holds both apart from the other Passes, and hands every message to the Gutter last.
- A Pass that wants a mark in the Gutter adds its own context to `GutterContext`, and the Gutter Pass decides which cell it goes in. For now `>` goes in cell 1, beside the text.
- The Current Line is no longer shown bold; the `>` beside it marks it, and its Matches are highlighted like any other.
- `cmd.Stream.GetWindow` returns two strings, not one.
- Amended (#23): the shown text and the Gutter cells now come from `headless.Logs.Window()`, as two slices from one read, hidden Lines left out of both, so their rows still line up (see ADR 0010); `cmd.Stream` has no `GetWindow`.
- A Pass that reads another Pass's context depends on running after it. The Filter runs first, before every other Pass, so it matches each Line's text as it came from the Log Feed.
- Amended (#17): the Executor builds the Filter, the Search and the Gutter itself, since every Executor needs them, and fixes their order: the Filter, then the other Passes it is given (`NewExecutor(stream, renderer, others...)`, the renderer styling the Search's Matches) in order, then the Search, then the Gutter. The same order holds for every message it hands on and for the Lines the Search's port reads.
- Amended (#16): with Lines left out, the Executor keeps the Log View full by growing the Window on read. It reads older Lines than the Window's (newer ones once it reaches the first Line) and runs the Passes over them until it has as many Lines the Filter does not hide as the Window's height (`reader.Stream.Height()`), reading at most `reader.DefaultCapacity` Lines beyond the Window, so a Filter that rarely matches cannot read the whole History on every render; past that, or once a read finds nothing (the Log File has failed to read), the Log View stays short. Each read takes in no more Lines than are still missing, so nothing is trimmed: `Lines()` returns the Window's own Lines, hidden ones included, and the Lines taken in. `reader.Window` itself never changes, so ending the Filter gives back the Window as it was, its newest end where it was. We rejected having the Filter grow the Window's height and ask the UI to render again through `tea.Cmd`s returned by `GetWindow` (the Lines it takes in can be hidden too, so it takes several renders to settle, the height must be shrunk back when the Filter ends, and `cmd` would depend on bubbletea). Scroll, centring the Current Line and the Search's first step still go by Line Number (#18).
- Amended (#24): there is no `reader.Window` or `reader.Stream.Height()`. The Window, and its height, live in the Executor (see ADR 0011), and growing it on read is unchanged.
